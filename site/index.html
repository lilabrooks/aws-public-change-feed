AWS Public Change Alerting turns approved public announcements into route-scoped Slack candidates for teams operating repeated AWS stacks. Each candidate records the source revision, matching evidence, potentially relevant environments, and exact policy release.

Value

A focused review queue from a broad AWS announcement stream.

General feed readers collect AWS news. This design adds declared service profiles, risk rules, environment mapping, and team routes. Platform teams receive explainable review candidates without granting the service access to customer AWS accounts.

Useful output

Evidence attached to every candidate

The result names the public source, service, risk evidence, announcement revision, route, audience, application version, and immutable configuration release.

Honest boundary

Potential relevance requires human review

Public announcements cannot prove account or resource impact. Operators use the candidate as a review prompt and confirm applicability with their existing AWS tooling.

Contracts

The contracts are executable, and the checks run against them.

Six strict JSON Schemas define the configuration, inventory, release, candidate, and delivery-request shapes. One canonical example bundle satisfies all of them at once, so the files prove both their individual shape and the behavior they share.

What the bundle proves

  • Each example passes the schema that owns it, and unknown fields are rejected.
  • Cross-file projections, references, and route scoping resolve across the whole bundle.
  • Release, candidate, and request hashes recompute to the committed values.
  • Deterministic identities reproduce across replays from fixed test vectors.

How a contract change is held

The bundle is the starting point for the negative tests: every mutation derived from it must fail validation.

  • Every rejected configuration or contract mutation carries a regression test.
  • A contract edit updates the schema, example, semantic validator, and tests together.
  • Edits touching identity recalculate every dependent hash in the same change.
  • Specification, ADRs, and this page move with the contracts or the build fails.

Validated contracts are not production evidence. These checks prove the repository agrees with itself. Production claims still require implemented runtime code, deployment tests, measured feed quality, and live delivery evidence.

AWS architecture

Deterministic matching before a durable Slack delivery boundary.

The design uses Lambda for scheduled and event-driven work, S3 for immutable releases and feed snapshots, DynamoDB for source and delivery state, SQS FIFO for destination-ordered transport, and CloudWatch plus SNS for operations.

01 · Acquire

Fetch approved public sources

The watcher applies HTTPS allowlists, DNS and IP checks, TLS verification, redirect rejection, response limits, parser limits, and per-feed checkpoints.

02 · Match

Create route-scoped evidence

Normalized announcements are matched against service aliases and distinct risk evidence, then mapped through static profiles to sorted route audiences. Terms are exact configured phrases, never stemmed, so a reviewer sees the literal wording that fired.

03 · Persist

Cross the durable outbox boundary

DynamoDB stores each candidate and delivery request before the watcher advances its feed checkpoint. Replays reconstruct the same logical identity.

04 · Deliver

Order, pace, and recover Slack work

SQS FIFO groups work by destination. The worker records posted, retryable, terminal, or unknown outcomes. An operator can close a delivery_unknown record as posted after finding the Slack message, reserve one audited retry after finding no post, or reserve one exact-request replay after correcting an ADR-021 allowlisted terminal condition. Terminal replay preserves the historical attempt count and exact release, refuses expired or immutable failures, and uses the existing paced dispatch path. A separate five-minute reconciler repairs bounded safe work, converts exact expired leases to unknown, and reports stale queued records without guessing that SQS lost them.

Why this architecture

The design follows the evidence and failure model.

Eighteen accepted ADRs govern the current architecture. ADR-017 narrowed an earlier design to public-feed intelligence and Slack delivery, removing account-scoped health, cost, and external-adapter paths from the product.

Scope and trust

Public feeds and static profiles

One public evidence class keeps the product narrow. Static mappings provide environment context without cross-account roles, resource discovery, or customer telemetry.

ADR-017 · Product scope
Evidence and identity

Deterministic rules and null-framed hashes

Reviewers can trace why a service and risk matched. Stable identity domains keep replay, edits, route isolation, and dedupe behavior testable.

ADR-002 · Route-scoped identity
State and transport

DynamoDB outbox with SQS FIFO

DynamoDB owns durable intent and outcomes. SQS handles ready-work transport and destination ordering; its time-limited dedupe cannot replace lasting state.

ADR-007 · Durable delivery
Replay and uncertainty

Immutable releases and explicit unknown outcomes

Exact S3 object versions reproduce the policy behind a candidate, and promotion of the active release is guarded by an S3 ETag precondition. Slack timeouts become delivery_unknown because an HTTP call cannot commit atomically with DynamoDB.

Evidence and status

Repository contracts are validated; Terraform roots are provisioned.

The current repository proves that its schemas, examples, semantic rules, deterministic identities, documentation, Terraform roots, and CI checks agree. It does not yet prove deployed AWS runtime behavior or live Slack delivery.

Available evidence

  • 6 numbered specifications and 17 accepted ADRs
  • 6 strict schemas with one valid cross-file example bundle
  • Deterministic matching scored against a labeled corpus of real and authored announcements
  • Feed acquisition with host allowlisting, address validation, and DOCTYPE-refusing parsing
  • A scheduled watcher composition root with exact release loading, conditional feed leases, response snapshots before parsing, compare-and-swap announcement history, deterministic response pages, and all-or-none checkpoint advancement
  • Watcher paging signals that separate bounded incompletion from unexpected faults, retain scheduled retries, and distinguish immediate fault pages from sustained 15-minute alarm periods
  • Watcher AWS adapters exercised through service mocks from an exact S3 release pointer and raw RSS response to S3 snapshot evidence and both DynamoDB tables
  • Route-scoped candidate construction rebuilt from the committed contract bundle
  • Durable outbox holding the feed checkpoint until candidate and delivery records exist
  • Due-work dispatch with state-version claims, FIFO dedupe reuse, cross-state batch limits, and explicit unknown-send evidence
  • DynamoDB delivery and SQS FIFO producer adapters exercised against service mocks
  • A one-minute dispatcher Lambda composition root with strict schedule validation, bounded results, function-scoped heartbeat, reserved concurrency one, and source-scoped exhausted-event handling
  • Slack delivery worker with exact release and application-artifact checks, release-bound candidate semantics, bounded plain-text rendering, conditional outcomes, pacing state, and retry-safe response classification
  • A public canonical Slack sample generated through the delivery renderer, with validation that rejects page or fixture drift and unsupported block shapes
  • FIFO Lambda handling with strict queue-body validation, remaining-time checks, ordered partial-batch failures, and fixed-name, dimensionless embedded metrics
  • Bounded recovery with exact expired-lease conditions, no automatic replay of unknown or unproven queued work, fixed state dimensions, and a scheduled Lambda composition root
  • A five-minute reconciler schedule with reserved concurrency one, separate exact package inputs, bounded retries, and a source-scoped standard runtime-failure queue
  • Preview-first delivery-DLQ control that verifies the exact FIFO queue pair and uses native SQS start, status, and cancellation actions without reading message bodies
  • Preview-first exact terminal replay with an explicit response allowlist, live-TTL and state-version guards, dedicated bounded audit history, and one reserved attempt that keeps the historical network-attempt count
  • Deterministic Python 3.12 packaging, a complete dependency lock, append-only digest-key publication, exact S3 object-version deployment inputs, and one injected sha256: application identity
  • Slack HTTP transport for incoming-webhook and bot-token modes, sharing feed acquisition’s address validation and pinned TLS connection, reporting only observed facts, and proving its no-bytes-sent claim row by row against a truth table
  • Credential readers for both accepted secret stores, Secrets Manager and SSM SecureString, requiring an encrypted parameter type, returning the stored value whole, and keeping it out of every message, repr, and log
  • Permanent credential faults resolved terminally while transient store failures reschedule with a bounded delay, no Slack call, and no pacing advance
  • Live feed screening that flags any production match the corpus does not represent
  • S3 release preconditions measured against the mock the publisher is tested on, including where that mock cannot stand in for S3
  • Release publication and promotion reproducing the committed release from the contract bundle's own bytes
  • Release loading that reads exact pinned versions, verifies hashes, validates the fetched bodies against their owned schemas, and binds internal versions to the pointer
  • Rollback that verifies a retained release before restoring it, with promotion times required to move forward so no later write can reproduce a retained version
  • A recorded decision on where the release contract is measured, including the one property the mock contradicts and the suite that will cover it
  • Terraform bootstrap and central roots provisioned with scoped backend access, least-privilege IAM, encryption, manifest and snapshot lifecycle rules, DynamoDB TTL, FIFO redrive, alarm publishing, and aggregate plus per-feed freshness views
  • Least-privilege policies checked against the deployed account with the IAM policy simulator, rather than by reading the Terraform
  • Semantic validation, deterministic identity vectors, and mutation tests
  • Repository quality, page drift, link, Mermaid, and HTML checks

Required implementation evidence

  • Corpus coverage of end-of-support announcements from real feeds
  • A controlled application-package retirement preview and, when naturally eligible packages exist, a separately authorized apply with retained-set verification
  • Publisher-side retirement of superseded releases, which S3 lifecycle cannot express safely
  • Applied watcher, dispatcher, worker, and reconciler infrastructure, plus controlled feed, dispatch, Slack, and recovery evidence
  • Feed, delivery, recovery, load, and security tests
  • Production preflight and confirmed Slack destination checks
