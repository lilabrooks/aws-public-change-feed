System

Fetch, match, write to DynamoDB, then queue for Slack.

Lambda runs the work. S3 stores immutable releases and feed snapshots. DynamoDB owns source and delivery state. SQS FIFO carries destination-ordered work to Slack.

  1. Acquire

    Fetch approved hosts with TLS, DNS and IP checks, redirect rejection, byte limits, parser limits, and per-feed checkpoints.

  2. Match

    Normalize title and summary text, merge duplicate URLs across feeds, then apply configured service aliases, risk phrases, profiles, and routes.

  3. Persist

    Write route-scoped candidates and delivery requests before advancing the feed checkpoint.

  4. Deliver

    Dispatch due work through SQS FIFO. The worker applies destination pacing and records the observed Slack outcome.

  5. Recover

    The reconciler retries due work and turns expired sending leases into delivery_unknown. Operator commands require the current state version before closure or replay.

What does the delivery record catch?

SQS hands each request to a Lambda worker, and the worker calls Slack. Four concrete failures explain why the service keeps a separate DynamoDB record.

Watcher stops
The watcher saves a pending_queue record before moving the feed checkpoint. If it stops before calling SQS, the dispatcher finds the saved record and queues it. If the save never finished, the next watcher run rebuilds the candidate from the old checkpoint.
Message returns
Lambda can receive the same SQS message again. The worker checks DynamoDB first. A posted record makes it acknowledge the message without posting to Slack twice, even after SQS FIFO’s 5-minute send-deduplication window.
Slack says retry
When Slack returns 429 with a retry time, the worker saves that time and acknowledges the current queue message. The dispatcher queues a new attempt later. The Lambda does not sit idle and sleep.
Slack answer is lost
Slack may accept a post just before the worker times out. Post-MVP recovery evidence confirmed the state transition and zero additional calls for the controlled expired record; it did not prove that a naturally expired network attempt sent nothing. The record becomes delivery_unknown, and automatic delivery stops until an operator checks Slack. A found post can be recorded, a conclusive no-match can authorize one audited replay, and an inconclusive search leaves the record unchanged.

A direct SQS-to-Lambda-to-Slack path is smaller when repeated posts and a short outcome history are acceptable. This service keeps the record so those four failures have a saved next step. It does not claim exactly-once Slack delivery. ADR-004 and ADR-007 define the boundary.

Required rules

Public feeds only. DynamoDB owns delivery history.

26 accepted ADRs define input scope, ID fields, state transitions, retries, and operator recovery.

Inputs
The runtime reads public feeds and static profiles. It has no customer-account credentials, resource discovery, telemetry, or remediation access. ADR-017
Candidate IDs
Candidate IDs include the announcement revision, service, risk, route, audience, and release. Reprocessing the same inputs produces the same ID. ADR-002
Delivery state
DynamoDB stores each request and outcome. SQS FIFO carries ready work in order for each Slack destination. ADR-007
Source-state lifecycle
Active feed checkpoints do not expire. Announcement and response-page history use exact-release TTL metadata. Legacy rows use a bounded conditional migration under a temporary scan role that is removed after the result is recorded. Removed feeds use exact-feed retirement and compaction plans under a permanent session-tagged role; same-name restoration requires the original URL hash. ADR-025
DynamoDB recovery
Both primary state tables use 35-day point-in-time recovery. The central source also enables DynamoDB deletion protection on that pair; isolated preflight tables keep it disabled so their reviewed teardown can still remove them. One proof records restore-request identity, complete restored-table verification, a disabled-trigger cutover, rollback to the primary pair, trigger restoration, and separately authorized cleanup. A CloudTrail-only role supplies digest-bound request evidence when an active table omits its restore summary; that evidence does not establish table contents by itself. L-41’s dev recovery proof is complete: it traversed all six stages, and all four disposable restore tables were deleted and confirmed absent. ADR-027 ADR-028
Slack timeout
A timeout becomes delivery_unknown. An operator checks Slack before choosing closure or one audited retry. ADR-004

Live operation

Park between tests. Restore only for a bounded live window.

Supervised short-window qualification passed on September 8, 2026: unpark/early-park, deadline cleanup after losing the local waiter, and the fixed live observation. M4 / L-58 records the lifecycle result and closure state. Unattended use remains gated by L-59, outside M4. Earlier readiness results retain their original scope.

Merging a PR runs repository checks and publishes this GitHub Pages site. Applying Terraform changes to AWS is a separate operator action.

Park
Disable the watcher, outbox-dispatcher, and recovery-reconciler EventBridge rules and the delivery FIFO mapping on the Slack worker. Set reserved concurrency to zero on all five functions, including shadow. Delete deployment CloudWatch metric alarms and the dashboard; recreate eligible monitoring during activation. Application log/metric publishing stops after in-flight runtime work ends.
Retain
Keep packages, releases, queues, durable delivery state, secrets, logs and their retention, and DynamoDB PITR. Retained log/S3/DynamoDB storage, PITR, secrets, and control resources can still incur charges. Builds and requests add usage while operating. Failure-only notification rules remain available while parked. Unpark can resume retained asynchronous work; parking does not purge it or prove an empty async queue.
Unpark and test
With reviewed private LIVE_CONFIG inputs and fresh per-use checks, use make live-unpark WINDOW=90m for a manual session, or make live-test WINDOW=90m for observation followed by parking. Add CASE=delivery for the one-attempt delivery proof. make live-park requests early cleanup; make live-status reads controls and the owner/deadline. These are separate operations. Keep an operator available through terminal results and verified parking, with recovery for failed or uncertain cleanup. Park when evidence is complete; never extend a quiet sample for a match.
Window limits
User-selected durations include setup and cleanup: ordered values such as 90m, 2h, or 1h30m, with minimums of 68 minutes for manual/observation and 78 minutes for delivery, up to 364 days. Repeated unpark keeps the original deadline. Step Functions owns cleanup beyond the local terminal’s lifetime, but AWS delays, retries, and recovery failures can overrun the target. Measured early-park and deadline samples do not establish worst-case budgets or net savings. Unchanged short tests need not repeat the first-use deadline-loss protocol.
